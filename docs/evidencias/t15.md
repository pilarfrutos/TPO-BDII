# T15 - Concurrencia y fallos parciales

La prueba integradora reutiliza los escenarios reales de q14 y q15 en bases
temporales de MongoDB. Publica en la instancia `neo4j-test` y simula la
indisponibilidad mediante una conexión a un puerto sin servicio. Después
repite la publicación en la instancia de prueba.

```sh
docker compose up -d --wait mongo mongo-init neo4j-test
python3.12 tests/servicios/verify_t15.py --evidencia
```

## Resultados observados

| Escenario | Resultado esperado y observado |
| --- | --- |
| Dos ventas por el mismo stock | Una venta se confirmó y la otra recibió `stock_insuficiente`. Ocho unidades iniciales quedaron en tres; nunca hubo saldo negativo. |
| Última dispensa de una receta | Cuatro ventas compitieron por la última dispensa de RC002. Una prosperó, tres recibieron `receta_no_vigente`, quedó una sola venta y la receta terminó 3/3. |
| Reintentos de la misma operación | Cuatro llamadas con el mismo `id_venta` produjeron una respuesta inicial y tres `repetida: true`. Se creó un detalle y se descontó una unidad. |
| Falla después de actualizar receta | La venta, su detalle y la dispensa eran visibles dentro de la transacción. El fallo revirtió todo. |
| Falla después de descontar stock | q15 había reducido L007 dentro de la transacción. El fallo restauró el lote y dejó ausentes venta y detalle. |
| Neo4j inaccesible | La sincronización devolvió `ErrorSincronizacion`; el grafo conservó el teléfono anterior y no presentó el cambio pendiente. |
| Recuperación de Neo4j | Al restablecer la conexión a la instancia de prueba se publicaron 193 registros y el cambio apareció. |

Los estados completos antes y después de las transacciones están en las
[evidencias de q14](q14.md) y [q15](q15.md).

## Garantías demostradas

- MongoDB serializa las escrituras que compiten por el mismo lote o receta.
- El stock nunca queda negativo y una operación rechazada no deja efectos parciales.
- `id_venta` actúa como clave de idempotencia para no repetir ventas, dispensas ni
  descuentos.
- Venta, detalles, receta y todos los lotes se confirman o revierten juntos.
- MongoDB y Neo4j no tienen una transacción distribuida. Una falla del grafo no
  revierte una venta confirmada; la aplicación informa el error y la proyección se
  recupera repitiendo la sincronización desde MongoDB.
